# EasyBigTrans Implementation Guide

This document is for **you** (the maintainer). It walks through:

1. Getting the pipeline running for the first time
2. Debugging common issues
3. Adapting it to your existing 100+ project data
4. Extending it (STAR, Salmon, meta-transcriptome) later

---

## Day 1: Get the skeleton running

### 1.1 Install Snakemake

```bash
conda create -n easybigtrans -c bioconda -c conda-forge \
    snakemake=8 mamba pandas -y
conda activate easybigtrans
snakemake --version    # should print 8.x
```

### 1.2 Verify the project loads

From the repo root:

```bash
snakemake -n --use-conda
```

A successful dry-run prints a job summary like:

```
Job stats:
job                       count
----------------------  -------
fasterq_dump_paired         12
fastp_paired                12
hisat2_build                 2
...
```

If you instead see a Python error from `common.smk`, fix the input tables
(see 1.3) before going further.

### 1.3 Common first-run errors

**`FileNotFoundError: sra_dir does not exist`**
The `sra_dir` column in `config/projects.tsv` is wrong or unreadable. Paths
must be absolute and contain `.sra` files directly (not in subfolders).

**`KeyError` on a species name**
Every species mentioned in `projects.tsv` must have a matching row in
`species.tsv`. Names are case-sensitive.

**`ValueError: No .sra files found`**
The SRA directory exists but contains no `.sra` files. Make sure you ran
`prefetch` or downloaded the files first; EasyBigTrans does not download
SRAs for you (by design — `prefetch` retries and resume policies are
project-specific).

### 1.4 Run on a tiny test project

Pick the smallest project you have (a 4-sample Arabidopsis study with
~3 GB total fastq is ideal) and edit `projects.tsv` to contain only that
project. Then:

```bash
# Run just the QC + alignment for one sample to verify everything works.
snakemake --use-conda --cores 8 -- \
    results/PRJNA_TEST/bam/SRR1234567.sorted.bam
```

Snakemake will create the Conda environments the first time (5–15 min)
and cache them under `.snakemake/conda/`. Subsequent runs reuse them.

## Day 2–3: Run a full project end-to-end

```bash
snakemake --use-conda --cores 32 -- \
    results/PRJNA_TEST/counts/CountMatrix.csv \
    results/PRJNA_TEST/multiqc/multiqc_report.html
```

Sanity checks after it finishes:

| File | What to check |
|------|---------------|
| `bam/*.sorted.bam` | `samtools flagstat` shows expected mapping rate (>70% for clean libraries) |
| `qc/fastp/*.html` | Adapter content, Q30 fraction, duplication look sensible |
| `counts/CountMatrix.csv` | Row count ≈ number of genes in the GTF; column count = sample count |
| `multiqc_report.html` | All sections populated, no missing samples |

Compare CountMatrix totals against what you got from the old bash pipeline
on the same project. Differences > 1% per sample are worth investigating —
likely due to `featureCounts -p` flag handling or different fastp trimming.

## Day 4+: Bring in your existing 100+ projects

You probably don't want to re-align everything you've already processed.
Two practical strategies:

### Strategy A: archive old, run new with EasyBigTrans

For projects you already finished, just keep the old `CountMatrix.csv` and
note in your records which pipeline produced it. EasyBigTrans takes over
for new projects.

### Strategy B: re-run a subset for the paper

For the case study in your paper, **re-run** 20–30 representative projects
through EasyBigTrans. This gives you:

- A consistent, reproducible result set generated by the published tool
- Direct numbers (runtime, memory, mapping rate) to put in the paper
- A test of the pipeline at realistic scale

Don't try to re-run all 100+ — the case study only needs a few dozen.

### Strategy C: side-by-side comparison for benchmark

Pick 3–5 projects you've already processed with the old bash scripts and
re-run them with EasyBigTrans. Compute correlation between count matrices
(should be > 0.999 if both pipelines are using HISAT2 + featureCounts the
same way). This becomes a reproducibility figure in the paper.

## Performance tuning

The defaults in `config.yaml` assume a 64-thread server. If yours differs:

- **Threads per rule**: edit the `threads:` block in `config.yaml`. Total
  parallelism is controlled by the `--cores N` flag at runtime.
- **Memory**: HISAT2 index building peaks at 12 GB for tomato-sized genomes,
  ~40 GB for wheat-sized ones. If you OOM, lower `hisat2_build` threads.
- **Disk**: trimmed fastq is the biggest consumer. Set
  `keep_trimmed_fastq: false` in `config.yaml` to delete them after counts
  are made.

Recommended settings for a 32-core / 128 GB server (per-project, multiple
samples running in parallel):

```yaml
threads:
  fasterq_dump:   4
  fastp:          8
  hisat2_build:  16
  hisat2_align:   8
  samtools:       4
  featurecounts: 16
  eggnog:        16
```

Then run with `--cores 32`. Snakemake schedules independent jobs concurrently.

## Debugging when a rule fails

Snakemake will tell you which rule failed and which log to read. Quick map:

| Failed rule | First place to look | Common cause |
|-------------|---------------------|--------------|
| `fasterq_dump_*` | `results/PROJECT/logs/fasterq_dump/SAMPLE.log` | corrupted .sra, not enough /tmp space (set `TMPDIR` to a big disk) |
| `fastp_*` | `results/PROJECT/logs/fastp/SAMPLE.log` | truncated fastq (re-extract the SRA) |
| `extract_splice_exon` | `results/logs/index/SPECIES_extract.log` | weird GFF format; verify it has `exon` features with `transcript_id` or `Parent` |
| `hisat2_build` | `results/logs/index/SPECIES_build.log` | OOM (lower threads) or bad FASTA |
| `hisat2_align_*` | `results/PROJECT/logs/hisat2/SAMPLE.log` | low mapping rate → wrong species assignment? |
| `featurecounts` | `results/PROJECT/logs/featurecounts.log` | `-p` flag mismatch for mixed-layout projects |

Re-run a specific failed rule with verbose output:

```bash
snakemake --use-conda --cores 8 \
    --rerun-triggers mtime \
    -p --verbose -- \
    results/PRJNA_TEST/bam/SRR1234567.sorted.bam
```

## Extending the pipeline

### Adding STAR as an alignment option

1. Add `workflow/envs/star.yaml` with `star=2.7.11a`.
2. Create `workflow/rules/align_star.smk` mirroring `align.smk`.
3. Add a `aligner: hisat2` field to `config.yaml`.
4. In `common.smk`, swap the BAM target rule based on `config["aligner"]`.

Keep both rule files; let users choose.

### Adding Salmon (pseudo-alignment)

Salmon needs a transcriptome FASTA, which is not currently in `species.tsv`.
Add a `transcripts_fa` column and an `index_salmon` rule. Quantification
produces `quant.sf` files instead of count matrices — write a small Python
script to merge them with `tximport`-style logic.

### Meta-transcriptome mode (your next paper)

For microbial meta-transcriptome you'll want:

- HUMAnN3 or a custom Bowtie2/Diamond pipeline against a reference DB
- Per-sample taxonomic profiling (Kraken2 or MetaPhlAn4)
- Functional binning

Best to fork EasyBigTrans into a sibling project rather than bolting it on,
because the assumptions (one genome per project, gene-level counts) don't
hold for meta-transcriptome.

## What I deliberately left out, and why

- **No automatic genome download.** Tested; every species names its files
  differently (Ensembl Plants vs NCBI vs Phytozome vs published supplements),
  and "wrong genome silently downloaded" is the worst failure mode. Better
  to make the user point to a real file.
- **No SLURM/cluster profile.** Easy to add later via Snakemake's
  `--profile` mechanism, but adds confusion for a local-server tool.
- **No DESeq2 wrapper.** The downstream user usually has very specific
  designs (factor combinations, batch effects). One-size-fits-all wrappers
  do more harm than good.
- **No `setup.py` / `pip install`.** This is a Snakemake project, not a
  Python package. Cloning the repo and editing `config/` is the intended
  workflow.

## Checklist before your paper submission

- [ ] Pipeline runs end-to-end on at least 3 projects from different species
- [ ] CountMatrix outputs are sample-name-consistent across projects
- [ ] MultiQC reports look clean (no missing modules)
- [ ] Runtime + RAM logged for each project (`/usr/bin/time -v`)
- [ ] CountMatrix correlation > 0.999 with old pipeline (reproducibility check)
- [ ] eggNOG annotation worked for at least one non-model species
- [ ] README and config templates are filled in with real example values
- [ ] GitHub repo is public, with a tagged release matching the paper
- [ ] Zenodo DOI minted for the release

---

## A note on what NOT to do

- Don't add features the paper doesn't need. Each new feature is a new
  failure mode and reviewers will ask if it's tested.
- Don't refactor the directory structure once you start collecting case
  study data — paths in your figures will need to match the published code.
- Don't promise differential expression in the abstract. The tool produces
  a count matrix; DE analysis is the user's job, and saying so is honest
  scoping, not a weakness.
